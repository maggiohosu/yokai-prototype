적 240마리(절반)를 지운 뒤 실제 보충으로 채운 측정(시드 731·732, 60fps 프레임 기준, 한 프레임 보충 상한 6마리)이다. 세 단계 모두 240/240마리를 화면 밖에 채웠고(실패 0, 화면에 걸친 것 0), 목표 480에 닿는 데 1단계 2.47초, 3단계 2.35초, 5단계 2.32초였다(상한 3마리일 때는 5.13·4.70·4.57초). 1920 × 1080(DPR 1)에서도 같은 값이었다. 1단계에서 이 화면의 시야가 맵의 44%를 덮지만 일반 규칙(화면 밖 여유 유지)으로 자리를 찾았다.

적끼리 먹는 소모가 있는 실제 판(플레이어가 걷고 쏘며 60fps로 60초)에서는 보충을 키우고(묶음 4 × 6, 프레임당 6마리) 새로 놓인 적에게 실제 5초 유예(`world.spawnGraceSec`)를 줘서 평균 인구가 1단계 474.8마리(최저 428), 2단계 475.3마리(최저 449), 3·4·5단계 478·479·480마리다(시드 731~734, 3단계 이후 731). 원인 분리·채택 근거는 [변경 이력 16](plan.md#변경-이력-16--맵-추가-14적-퍼뜨리기-사용자-지시-2026-11-23)이다. 이 측정과 위 여섯 장면은 큰 적 3배(`difficulty.bigMult` 3, 변경 이력 17)를 넣은 트리에서 다시 쟀다.

`?stress=abilities|weapons`는 한 변 4000, 적 72마리를 그대로 쓴다(`perf-field`가 `[4000, 72, 1000]`을 단언한다. 마지막 값은 새 `worldFor(1).size`다). `perf-abilities`의 능력 시험이 예전에는 `CONFIG.world.population` 72를 읽었기 때문에, 판 인구가 480이 된 뒤에도 72마리로 고정되도록 상수를 뒀다.

### 일반 판의 첫 배치와 보충

노말 저장 슬롯으로 일반 판을 시작해 시드 731~735에서 축소 전 기준 빌드와 리뷰 시점 통합 작업본을 측정했다. 초기 시간은 `createField` 진입부터 마지막 시작 적 배치까지의 벽시계 중앙값이며, 형태 텍스처를 준비하는 비용을 포함한다. 보충은 24마리를 제거하고 이동·전투만 잠시 멈춘 뒤 실제 보충 루프에 1/60초씩 전달했다. 복구 시간은 목표에 도달한 프레임 수 × 1/60초다. 시작 화면 마릿수는 카메라 안에 중심이 있는 적의 중앙값이다.

모든 판이 첫 업데이트 전에 목표 인구에 도달했다. 위치 탐색 한 번은 후보를 최대 90회 검사한다. 5단계에서 시작 고리 탐색이 실패한 76회는 같은 크기와 단계로 맵 전체에서 다시 시도해 모두 배치했다. 보충은 단계별 120마리 모두 화면 밖에 생성됐고, 24마리를 복구하는 데 모든 시드에서 20프레임이 걸렸다.

1단계의 CSS 배율은 변경 전후 모두 1.439486, Phaser 카메라 줌은 2.878972였다. 시드 731에서 플레이어 스프라이트는 51.18 CSS px, 첫 먹이는 31.88 CSS px 너비로 같았다. 844/2000 = 0.422가 기존 최소 배율 0.43보다 작아 이 기기의 성장 후 최소 배율도 같다. 2560px 너비의 화면에서 1단계의 하한은 1.28이며, 진화 연출 중 리사이즈도 새 하한을 따른다. 좌표가 판 밖인 부가 필드를 포함한 버전 1 슬롯도 해당 단계의 중앙에서 시작했다.

노드 시험에서는 맵·타일·진화 크기 기대값을 새 한 변에 맞췄다. 배회 속도와 시작 고리 검사는 현재 판의 중앙에서 실행하고, 카메라 검사는 진화한 단계의 실제 경계와 넓은 화면의 하한을 반영한다. 5단계 AI·충돌 보조 시험도 실제 단계 크기로 적을 배치한다.

리뷰 재검증에서 Node 24.20.0의 `node --test "tests/*.test.mjs"` 714개와 `src`·`tests`의 `node --check` 119개가 통과했다. Chrome을 연결한 `tests/perf-field.test.mjs` 16개도 통과했다. 아래 재측정 명령으로 여섯 부하 장면과 일반 판 보충 시험을 함께 실행할 수 있다. 보충 시험은 시드별 목표 도달 시간과 위치 탐색 결과를 `REFILL` 진단에 출력한다. 실기기 발열은 이 데스크톱 측정의 범위 밖이다.

## 변경 이력 10 적 인구 3배와 프레임 시간

데스크톱 Chrome에서 1·3·5단계 여의주·팔괘경 여섯 장면이 프레임·시뮬레이션·그리기 예산을 충족했다. 5단계 852마리의 평균 프레임 간격은 여의주 108.09→16.67ms, 팔괘경 112.89→16.67ms였다. 5단계 시뮬레이션 평균은 중간 빌드의 6.63·7.33ms에서 **4.69·4.53ms**로 줄었다. 수치는 장면별 다섯 실행의 중앙값이다.

## 시간표를 읽는 법

프레임 간격은 연속한 Phaser 업데이트 시작 사이의 벽시계 시간이다. 시뮬레이션은 이동·지각·조향·충돌·먹기·무기·상태 갱신과 게임 보충 및 시험 인구 복구에 걸린 CPU 시간이다. 그리기는 애니메이션·표식·발사체 등 화면 준비와 `prerender`부터 `postrender`까지 Phaser가 렌더 명령을 제출하는 데 걸린 CPU 시간의 합이다. GPU 자체의 실행 시간은 따로 계측하지 않았다. 프레임 간격에는 브라우저 페이싱, HUD, 엔진의 나머지 작업과 대기도 포함된다.

각 칸은 **평균 / p95**, 단위는 ms다. 각 실행의 180개 표본에서 먼저 평균과 nearest-rank p95를 구한 뒤, 다섯 실행의 각 통계에서 중앙값을 취했다. 프레임 간격의 예산은 평균 18ms, p95 25ms이고 시뮬레이션과 그리기의 예산은 각각 프레임당 평균 6ms다.

### 같은 이웃을 다시 검사하는 비용

중간 빌드의 5단계 시뮬레이션 평균은 여의주 6.63ms, 팔괘경 7.33ms였다. 180프레임 동안 팔괘경이 돈 계산 단계는 900번이었다. 먹기 루프가 이웃 칸 1,809,293개와 칸 안의 개체 1,609,746개를 방문했다. 지각·무기·생성 등 일반 반경 조회는 그 밖에 1,050,165칸과 614,374개체를 방문했다. 칸 방문 수에는 비어 있는 칸, 개체 방문 수에는 자기 자신과 중복 방문이 포함된다.

먼저 매 프레임 모든 적의 이웃을 원형 범위로 미리 조회했다. 팔괘경의 먹기 루프는 157,490칸으로 줄었지만 일반 반경 조회가 1,537,987칸으로 늘었다. 계수기를 끄고 순서를 바꾸며 세 번 대조하자 평균 시뮬레이션 중앙값이 여의주 6.05→6.44ms, 팔괘경 5.31→6.05ms였다. 이 방식은 제외했다.

채택한 방식은 프레임 시작 시 각 적의 몸을 8월드 단위 넓힌 사각형을 64단위 격자에 기록한다. 사각형이 한 칸도 겹치지 않으면 그 안에서 이동하는 두 적은 서로 먹을 수 없다. 이동 후 경계를 벗어나거나 몸이 크게 변하면 해당 계산 단계에서 전체 후보를 원래 순서대로 검사한다. 시험한 사각형 방식만 적용했을 때 팔괘경의 먹기 루프는 515,499칸, 759,412개체였다. 일반 반경 조회 횟수는 그대로였다. 이 판정은 먼 적의 이동 갱신을 묶어도 될 때를 고르는 데도 쓴다. 최종 이동·격자 변경까지 적용한 5단계 팔괘경에서 먹기 루프는 510,423칸, 738,703개체를 방문했다. 일반 반경 조회는 1,040,606칸, 597,140개체였다. 횟수 계측은 별도 실행에서 했으며 시간표의 실행에서는 껐다.

## 병목과 변경

1. **공용 적 표시**. 화면 밖 특수 적도 매 렌더 프레임에 14조각의 호를 만들었다. Phaser는 공유 Graphics에 쌓인 명령을 매번 처리했다. 화면과 겹치는 고리만 남기고, 회전하는 점선은 미리 계산한 단위원 좌표로 한 경로에 그린다. 단계 점은 1~5개의 점을 단계·상대 색·반지름(0.25 CSS px 간격)별로 한 번 구워 가시 개체 수만큼의 이미지를 재사용한다. 특수 적 구슬, 생명력 원호, 대요괴의 화면 가장자리 화살표는 계속 그린다.
2. **먹기와 AI**. 표식을 고친 직후 852마리 팔괘경 진단에서 그리기는 1.56ms, 시뮬레이션 본체는 9.13ms였고 이 중 먹기가 3.22ms였다. 현재는 128단위 격자의 칸 배열을 재사용하고, 충돌 가능성이 있는 칸을 원래 순서대로 검사한다. 화면 밖이며 플레이어와 640단위 넘게 떨어진 일반 적은 격자에서 고립된 경우 최대 다섯 단계의 이동을 한 번 계산한다. 중간 위치는 매 단계 보간해 투사체가 이동 경로를 검사할 수 있다. 화면 안·플레이어 근처·다른 적과 충돌 가능한 구역과 상태이상·맞수는 이동을 세분한다. 무기와 적탄의 발사·명중, 상태 타이머는 각 계산 단계에서 처리한다. 첫 프레임과 크기 변경 직후에는 현재 스크롤·화면 크기·줌으로 가시 영역을 구한다.
3. **보충과 프레임 지연**. 일반 보충과 시험 인구 복구는 각각 한 묶음에 격자 하나를 사용하고 새 적을 즉시 격자에 넣는다. 시험 복구에서 첫 생성이 실패하면 그 프레임의 시뮬레이션을 진행하고 다음 프레임에 다시 시도한다. 계산 단계 상한은 `ceil(0.05 × 3.9 × 1.1 ÷ (1/60)) = 13`이다. 5단계에서 20fps까지 허용된 프레임 시간을 모두 처리한다. 50ms보다 오래 걸린 일반 프레임에서는 게임 시계가 실제 시간보다 느려질 수 있다.

먹기 크기·단계 기준, 난이도별 생성 가중치, 보상, 발사·상태이상 수치와 몸집 상한은 기존 규칙을 쓴다. 멀리 떨어져 홀로 이동하는 적의 궤적은 달라질 수 있다. 같은 위치·상태에서 먹기 순서는 전체 격자와 대조했고, 근접 교전에서 여의주·팔괘경이 맞힌 대상과 피해, 먹기 순서, 이동 좌표도 세분 계산과 대조했다. 일반 적 스프라이트의 생명 주기는 유지하고, 이미지 재사용은 단계 표식에 적용했다.

### W5 공용 표식 재검증

기존 W5 주소 `?stress=weapons&w=yeouiju`와 `w=mirror`에서도 따로 확인했다. W5 조건인 1280 × 720, DPR 1, 적 72마리, +15 무기와 구슬 최대 120개를 유지하고 4.5초씩 한 번 실행했다. `fireGfx.renderWebGL`만 감싼 진단 실행이므로 위의 5회 시간표와 구분한다. [W5의 원래 측정](design-weapons.md#그리기계산-비용과-남은-수정)

중간 빌드의 5단계 팔괘경 852마리에서 Chrome의 프레임 제한과 GPU 수직동기화를 끈 별도 실행은 평균 간격 5.88ms, p95 7.30ms, 시뮬레이션 평균 4.24ms, 그리기 평균 0.97ms였다. 일반 60Hz 실행에서는 브라우저의 화면 갱신 주기도 프레임 간격에 반영된다.

### 규칙 및 실행 검증

Chrome의 일반 판을 단계별로 다시 시작해 216·480·852마리를 확인했다. 첫 단계의 216마리는 전부 1단계 적이었다. 세 판 모두 24마리를 제거하고 먹기·이동을 잠시 멈춘 뒤 실제 보충 경로를 돌렸을 때 **3 + 3 + 3 + 3마리**가 생겼다. 같은 일반 판에서 실제 계측 로그도 확인했다. `PERF update avg 1.04ms max 12.10ms render avg 0.36ms max 4.20ms enemies 216`

Node 24.20.0에서 `node --test "tests/*.test.mjs"` **692개가 통과**했고, `src`와 `tests`의 JavaScript 파일 **113개가 `node --check`를 통과**했다. 월드·생성 시험은 기존 정수 인구의 정확히 3배를 검사한다. 새 시험은 생성 실패와 재시도, 5단계 시간 상한, 첫 렌더와 리사이즈, 계측 리스너 해제, 이동·성장·생성 이후의 먹기 순서와 근거리 무기 명중을 검사한다. Chrome을 연결한 `tests/perf-field.test.mjs`도 14개 모두 통과했다.

## 다시 측정하기

첫 브라우저 일괄 실행은 장면 완료를 기다리다 한 차례 시간 초과가 났다. 같은 Chrome과 자산으로 HTTP/1.1 정적 서버에서 30회를 다시 실행해 위 표를 얻었다.

프로젝트 루트에서 `python -m http.server 8000 --bind 127.0.0.1 --protocol HTTP/1.1`로 시작한다. 가로 844 × 390, DPR 2에서 `http://127.0.0.1:8000/?stress=population&stage=5&w=mirror&seed=731`을 열면 콘솔의 `STRESS_REPORT`와 `window.__stressReport`에 결과가 남는다. `stage`는 1·3·5, `w`는 `yeouiju` 또는 `mirror`다. `initialStages`, `minSimStartCount`, `fires`, `hits`로 부하를 확인하고, `spawnMs`와 `submitMs`로 보충과 렌더 제출 시간을 구분한다. 일반 판은 `?perf=1`로 시작하면 업데이트와 렌더가 모두 끝난 120프레임마다 각 평균·최대 시간과 적 수를 콘솔에 출력한다.

설치된 Chrome과 Node용 Playwright가 있으면 별도 터미널에서 다음 명령으로 여섯 장면의 예산을 자동 검증할 수 있다. 이 PC처럼 Python용 Playwright를 쓰는 경우에는 함께 설치된 Node 드라이버 경로를 사용한다.

```powershell
$env:YOKAI_PERF_URL = 'http://127.0.0.1:8000/'
$env:YOKAI_PLAYWRIGHT = python -c "import pathlib,playwright; print(pathlib.Path(playwright.__file__).parent/'driver'/'package'/'index.mjs')"
node --test tests/perf-field.test.mjs
```

Node 프로젝트에서 `playwright`를 직접 가져올 수 있으면 `YOKAI_PLAYWRIGHT` 설정을 생략한다. 캐시한 동일 버전의 CDN 파일로 재현할 때는 `YOKAI_PHASER_JS`와 `YOKAI_FONT`에 각 파일 경로를 준다. 기본 규칙 시험은 `node --test "tests/*.test.mjs"`다.

같은 파일의 일반 판 60초 시험은 1~5단계에서 시작 직후와 60초 뒤의 몰림 지표 R이 0.9 이상인지, 1~5단계 모두 평균 인구가 목표의 95% 이상, 최저가 400 이상인지 확인하고 진단을 `LIVE` 줄로 낸다. 따로 돌리려면 `node --test --test-name-pattern="일반 판 60초" tests/perf-field.test.mjs`다(60fps 프레임으로 단계당 약 10~15초).

## 휴대폰에서 확인할 점

- 실제 Android Chrome과 iOS Safari에서 5단계 여의주·팔괘경을 각각 실행한다. 시작 직후와 15분 연속 플레이 뒤의 프레임 간격·시뮬레이션·그리기를 비교해 발열에 따른 변화를 확인한다.
- 실제 판에서 카메라가 움직이고 진화 직후 줌이 변할 때 단계 점, 특수 적 고리, 화면 밖 대요괴 화살표를 확인한다. DPR 2 이상의 작은 화면에서는 작은 점의 테두리와 화살표 식별도 함께 본다.
- 새 단계의 첫 진입, 보충이 몰리는 구간, 세로·가로 전환 뒤 재개를 별도로 확인한다. 위 시간표는 캐시와 렌더러가 예열된 데스크톱 결과다.
