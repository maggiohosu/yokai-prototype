# 적 인구 3배와 프레임 시간

여섯 장면 모두 변경 후 프레임 간격 평균의 중앙값이 **16.67ms**, p95는 **16.90~18.00ms**였다. 5단계 852마리에서 여의주는 평균 108.09ms에서 16.67ms로, 팔괘경은 112.89ms에서 16.67ms로 줄었다. **5단계 시뮬레이션은 6ms 예산 미달**이다. 최종 빌드의 중앙값은 여의주 6.63ms, 팔괘경 7.33ms였다.

## 측정 조건

2026년 11월 23일, Windows 11 Home 10.0.26300, Core i5-10400F(6코어·12스레드), RAM 15.9GiB, GeForce GTX 1660 SUPER에서 측정했다. Chrome 158.0.8127.36 헤드리스의 WebGL 렌더러는 ANGLE Direct3D 11을 사용했다. 화면은 가로 844 × 390 CSS px, DPR 2, 실제 캔버스 1688 × 780px였다. 정적 HTTP 서버가 게임의 ES 모듈을 그대로 제공했고, 모든 실행은 같은 Phaser 3.90.0 배포본과 Pretendard 글꼴을 사용했다.

기준 빌드는 `a3f3c0b`의 시뮬레이션·렌더링에 늘어난 인구·보충량과 동일한 측정 장치를 적용한 것이다. 개발 중에는 같은 PC에서 기준 빌드와 최적화 후보의 실행 순서를 번갈아 배치했다. 일반 적의 맞수 속성값을 기존 계약으로 복원한 뒤 최종 빌드 6개 장면을 각각 다섯 번 별도로 재측정했다. 아래 표의 전·후는 각각 기준·최종 빌드의 5회 결과다. 한 실행마다 브라우저 컨텍스트를 새로 만들고 60프레임을 예열한 뒤 연속 180프레임을 수집했다.

시드는 731, 난이도는 노말, 등급은 C, 무기는 +15다. 플레이어가 원을 그리며 움직이고 발사 버튼을 계속 누른다. 매 프레임 실제 단계 템포에 1/60초를 적용한다. 적끼리 먹거나 무기에 맞아 죽으며, 빈자리는 실제 생성 함수로 채운다. 표본마다 시뮬레이션 시작 시 목표 인구가 있었고 두 빌드의 시작 단계 분포와 발사 횟수가 일치했다. 시험 판은 저장 슬롯과 독립적으로 동작한다.

일반 판은 단계 배율과 인구 배율을 곱한 뒤 반올림한다. 1~5단계 목표 인구는 **216 / 344 / 479 / 648 / 853**이다. 측정 판은 종전의 정수 인구에 3을 곱한 **216 / 480 / 852**로 고정해 두 버전의 부하를 맞췄다. 일반 보충량은 기존 4마리 × `world.populationMult`로 계산한다.

## 시간표를 읽는 법

프레임 간격은 연속한 Phaser 업데이트 시작 사이의 벽시계 시간이다. 시뮬레이션은 이동·지각·조향·충돌·먹기·무기·상태 갱신과 게임 보충 및 시험 인구 복구에 걸린 CPU 시간이다. 그리기는 애니메이션·표식·발사체 등 화면 준비와 `prerender`부터 `postrender`까지 Phaser가 렌더 명령을 제출하는 데 걸린 CPU 시간의 합이다. GPU 자체의 실행 시간은 따로 계측하지 않았다. 프레임 간격에는 브라우저 페이싱, HUD, 엔진의 나머지 작업과 대기도 포함된다.

각 칸은 **평균 / p95**, 단위는 ms다. 각 실행의 180개 표본에서 먼저 평균과 nearest-rank p95를 구한 뒤, 다섯 실행의 각 통계에서 중앙값을 취했다. 프레임 간격의 예산은 평균 18ms, p95 25ms이고 시뮬레이션과 그리기의 예산은 각각 프레임당 평균 6ms다.

최종 빌드의 30회 모두 평균 프레임 간격 18ms와 p95 25ms를 지켰다. 가장 높은 실행 평균 간격은 16.95ms, 가장 높은 p95는 21.50ms였다. 5단계 시뮬레이션 평균은 여의주 5.70~10.71ms, 팔괘경 5.81~8.54ms였고 두 무기 모두 다섯 번 중 네 번이 6ms를 넘었다. 최종판과 후보판의 실행을 번갈아 추가 비교해도 CPU 시간의 편차가 컸다.

5단계에서는 프레임마다 852마리의 이동·충돌을 다섯 번 처리한다. 팔괘경을 함수별로 다시 잰 180프레임 중 21프레임이 시뮬레이션 6ms를 넘었다. 예산 이내와 초과 프레임의 평균을 비교하면 전체 시뮬레이션 4.63→7.78ms, 먹기 1.17→1.69ms, 무기 처리 0.06→0.81ms, 보충 0.15→0.50ms였다. 먼 적의 목표 속도를 추가로 캐시하는 방법과 상태 기본값을 지연 생성하는 방법도 각각 세 번씩 대조했으나 중앙값 개선이 없어 두 변경을 제외했다. 다음 측정 대상은 같은 프레임에서 이동·먹기·무기가 반복 조회하는 이웃 칸 수와 후보 수다. 위치나 크기가 바뀐 개체 주변의 후보만 다시 모아도 모든 계산 단계에서 실제 먹기·명중 판정을 유지할 수 있는지 검증할 필요가 있다.

## 병목과 변경

1. **공용 적 표시**. 화면 밖 특수 적도 매 렌더 프레임에 14조각의 호를 만들었다. Phaser는 공유 Graphics에 쌓인 명령을 매번 처리했다. 화면과 겹치는 고리만 남기고, 회전하는 점선은 미리 계산한 단위원 좌표로 한 경로에 그린다. 단계 점은 1~5개의 점을 단계·상대 색·반지름(0.25 CSS px 간격)별로 한 번 구워 가시 개체 수만큼의 이미지를 재사용한다. 특수 적 구슬, 생명력 원호, 대요괴의 화면 가장자리 화살표는 계속 그린다.
2. **먹기와 AI**. 그림 병목을 제거한 852마리 팔괘경 진단에서 그리기는 1.56ms였고, 시뮬레이션 본체는 여전히 9.13ms였다. 이 중 먹기 처리에 3.22ms가 들었다. 격자는 점유한 칸 배열을 재사용하고, 먹기 후보는 중간 배열 없이 인접 칸에서 바로 판정한다. 시야 밖이면서 플레이어에서 640월드 단위보다 먼 적의 표적·조향 갱신은 네 계산 단계에 분산한다. 이동·충돌·상태이상·적탄 처리는 매 단계 실행한다. 감속·단위 방향·회전 보간의 반복 계산을 줄였고, 지각 비교에는 제곱거리를 사용한다. 고정 시드 5단계에서 셀 너비 128을 사용한 시뮬레이션이 320을 사용했을 때보다 빨랐다.
3. **보충과 프레임 지연**. 한 보충 묶음 12마리를 프레임당 최대 3마리씩 배치한다. 같은 묶음에서 새로 놓은 적도 즉시 생성 격자에 넣어 겹침을 막는다. 시뮬레이션은 프레임당 최대 8단계, 단계당 최대 1/60 시뮬레이션 초다. 한 번 밀리면 다음 프레임이 따라잡고, 지연이 계속되면 최대 8단계분까지만 이월한다. 이때 게임 시간이 실제 시간보다 느려질 수 있다.

먹기 크기·단계 기준, 난이도별 생성 가중치, 보상, 발사·상태이상 수치와 몸집 상한은 기존 규칙을 쓴다. 원거리 적의 궤적과 여러 적이 동시에 겹칠 때의 처리 순서는 달라질 수 있다. 일반 적 스프라이트의 생성·소멸 방식은 유지했다. 확인된 병목은 표식 명령 처리와 AI·충돌이었고, 이미지 재사용은 화면에 나타나는 단계 표식에 적용했다.

### W5 공용 표식 재검증

기존 W5 주소 `?stress=weapons&w=yeouiju`와 `w=mirror`에서도 따로 확인했다. W5 조건인 1280 × 720, DPR 1, 적 72마리, +15 무기와 구슬 최대 120개를 유지하고 4.5초씩 한 번 실행했다. `fireGfx.renderWebGL`만 감싼 진단 실행이므로 위의 5회 시간표와 구분한다. [W5의 원래 측정](design-weapons.md#그리기계산-비용과-남은-수정)

| 무기 | 공용 Graphics 제출 전 → 후(ms/렌더 프레임) | 전체 평균 간격 전 → 후(ms) | 변경 후 p95(ms) | 변경 후 실제 명중 |
|---|---:|---:|---:|---:|
| 여의주 | 7.40 → 0.42 | 18.51 → 16.95 | 25.20 | 769 |
| 팔괘경 | 10.77 → 0.47 | 18.20 → 17.40 | 24.40 | 187 |

5단계 팔괘경 852마리에서 Chrome의 프레임 제한과 GPU 수직동기화를 끈 별도 실행은 평균 간격 5.88ms, p95 7.30ms, 시뮬레이션 평균 4.24ms, 그리기 평균 0.97ms였다. 일반 60Hz 측정에서 평균 간격이 16.67ms에 모이는 데에는 디스플레이 페이싱이 작용한다.

### 규칙 및 실행 검증

일반 게임의 새 판 시작을 Chrome에서 확인했다. 1·3·5단계 시작 개체 수는 목표와 동일한 216·479·853마리였고, 1단계의 216마리는 모두 1단계 적이었다. 각 판에서 적 24마리를 제거한 뒤 먹기·이동을 잠시 멈추고 실제 보충 경로를 네 프레임 진행하자 **3 + 3 + 3 + 3마리**가 생겼다. 5단계 화면에서 단계 점과 회전 고리, HUD도 확인했다.

Node 24.20.0에서 `node --test "tests/*.test.mjs"` **686개가 통과**했다. 인구가 바뀌어 기존 월드 크기·생성 시험의 기대 마릿수가 갱신됐다. 먹기·단계·난이도·상태이상 규칙의 기대값은 그대로다. `src`와 `tests` 안의 JavaScript 파일 **113개가 `node --check`를 통과**했다. 개발 중 독립 브라우저 시험에서는 5단계 CPU 평균 중앙값이 5.65ms·5.55ms로 예산을 통과한 실행도 있었다. 최종 합격 여부는 위 표의 재측정 결과로 판정했다.

## 다시 측정하기

프로젝트 루트에서 `python -m http.server 8000 --bind 127.0.0.1`로 시작한다. 가로 844 × 390, DPR 2에서 `http://127.0.0.1:8000/?stress=population&stage=5&w=mirror&seed=731`을 열면 완료 시 콘솔의 `STRESS_REPORT`와 `window.__stressReport`에 결과가 남는다. `stage`는 1·3·5, `w`는 `yeouiju` 또는 `mirror`다. `initialStages`, `minSimStartCount`, `fires`에서 실제 부하를 확인하고, `spawnMs`와 `submitMs`에서 보충과 렌더 제출 시간을 따로 볼 수 있다.

설치된 Chrome과 Node용 Playwright가 있으면 별도 터미널에서 다음 명령으로 여섯 장면의 예산을 자동 검증할 수 있다. 이 PC처럼 Python용 Playwright를 쓰는 경우에는 함께 설치된 Node 드라이버 경로를 사용한다.

```powershell
$env:YOKAI_PERF_URL = 'http://127.0.0.1:8000/'
$env:YOKAI_PLAYWRIGHT = python -c "import pathlib,playwright; print(pathlib.Path(playwright.__file__).parent/'driver'/'package'/'index.mjs')"
node --test tests/perf-field.test.mjs
```

Node 프로젝트에서 `playwright`를 직접 가져올 수 있으면 `YOKAI_PLAYWRIGHT` 설정을 생략한다. 캐시한 동일 버전의 CDN 파일로 재현할 때는 `YOKAI_PHASER_JS`와 `YOKAI_FONT`에 각 파일 경로를 준다. 기본 규칙 시험은 `node --test "tests/*.test.mjs"`다.

## 휴대폰에서 확인할 점

- 실제 Android Chrome과 iOS Safari에서 5단계 여의주·팔괘경을 각각 실행한다. 시작 직후와 15분 연속 플레이 뒤의 프레임 간격·시뮬레이션·그리기를 비교해 발열에 따른 변화를 확인한다.
- 실제 판에서 카메라가 움직이고 진화 직후 줌이 변할 때 단계 점, 특수 적 고리, 화면 밖 대요괴 화살표를 확인한다. DPR 2 이상의 작은 화면에서는 작은 점의 테두리와 화살표 식별도 함께 본다.
- 새 단계의 첫 진입, 보충이 몰리는 구간, 세로·가로 전환 뒤 재개를 별도로 확인한다. 위 시간표는 캐시와 렌더러가 예열된 데스크톱 결과다.
